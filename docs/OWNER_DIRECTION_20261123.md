## 3. D-2 交付路线：ERPNext 自建 + 单客户定制 + Web 域名部署

### 3.1 已确定

- 底座保持 ERPNext，不转向管家婆／金蝶商业产品或二次开发授权。
- 目标客户是**一家具体的五金工具公司**，系统按其需求定制，不是通用 SaaS 产品。
- 最终形态是部署到 Web 上的一个域名，对方通过浏览器访问使用。

### 3.2 由这条结论派生的新约束

D-2 把项目性质从「可丢弃的 Phase 0 技术验证」改为「面向真实客户的定制系统」。随之而来以下事项从「不需要」变成「需要」，此前都不在 R1 首版范围里：

| 新增约束 | 来源 | 当前状态 |
|---|---|---|
| 需要真实的域名、HTTPS 证书与对外入口 | D-2「部署到 Web 上一个域名」 | 未开始；Phase 0 全部为 localhost |
| 需要真实并发账号与角色，而不是五类合成用户 | D-2「方便他们使用」 | 未开始；现为五类合成角色 |
| 需要正式的备份、恢复与故障处置 | D-2 生产使用 | 未开始；仅一次性环境 |
| 需要终端用户（文员／仓管／采购／财务）的操作手册与培训材料 | D-2「方便上手」 | 未开始；`OPERATOR_SOP.md` 面向验证者 |
| 需要数据保留、导出与退出条款（对方何时能带走自己的数据） | D-2 单一客户长期使用 | 未开始 |
| 需要确认 ERPNext 升级策略与维护责任 | D-2 长期运行 | 未开始；当前镜像钉死 `v16.33.0` |

### 3.3 租户模型（已闭合）

**所有者已确认：仅服务这一家客户。** 租户模型定为单租户，见 DEC-018。

- 不引入多租户隔离、租户路由、按租户计价模型或 SaaS 商业化功能。
- **不得引入任何"未来可能多租户"的推测性设计。**
- 省下的工程量全部投入 D-3／D-6 的操作体验重做与 N-3／N-4／N-5 三项新增功能。
- 若出现第二家客户，作为独立决策重新开启，届时隔离成本是已知且已定价的，而不是现在预付。

### 3.4 与既有文档的关系

D-2 不推翻 `docs/FIRST_RELEASE_SCOPE.md` 的 R1 功能范围，但**改变了发布门槛的性质**：

- 现有 Phase 1 定义为「部署已验收的 RC」，前提是**已有确定的基础设施**。
- D-2 把「基础设施选型 + 域名 + 真实身份 + 真实岗位 UAT」本身变成了需要交付的工作项，而不只是环境准备。

`docs/ROADMAP.md` 的 Phase 1 已据此扩写。

## 4. N-1 底座替换路线：分层抽离（已定，见 DEC-022）

### 4.1 所有者原意

等基本需要的功能完善可用之后，逐步把原有的 ERPNext 底座换掉，改成自己开发的内容，脱离这个底座——无论前端还是操作逻辑已经在这么做了，后续还需要进一步换掉，改成更好的底层代码逻辑和设计。

### 4.2 ERPNext 底座现在替我们扛着什么

| 层 | ERPNext 已实现且**已被本项目验证** | 验证证据 |
|---|---|---|
| 复式记账内核 | 借贷平衡、科目表、期间结转 | P0 报表验证、总账核对 |
| 库存核算 | 移动平均、负库存拦截、跨仓调拨、盘点调整 | P0 库存验证、库存流水对账 |
| 税务引擎 | 价内价外、行级税额、折算税费率 | 报价 170.10 元 / 255.15 元实测 |
| 审批流引擎 | 状态机、条件转移、Workflow 引擎 | C0 生命周期、九类工作流 |
| 权限模型 | 角色、User Permission、字段 permlevel | 九岗位权限矩阵、越权拒绝 |
| 报表引擎 | 库存余额/流水、采购/销售分析、应收/应付、总账 | 七类原生报表 |
| 文档 + 表单框架 | DocType 引擎、表单、列表、打印、PDF | 十类中文 PDF 模板 |

**这些不是"还没验证的半成品"，是本项目 11 月全部工作量的承载物。** 09-01 至 11-22 的 9 个证据 JSON、42 项测试、C0/M1/A1 三道演练，全部建立在它们之上。

### 4.3 自研同等内核的成本估算

| 模块 | 熟练开发者估算 | 备注 |
|---|---|---|
| 复式记账内核 | 2–3 人月 | 借贷平衡、科目、期间、反结账 |
| 库存核算 | 2–3 人月 | 批次、序列号、成本算法 |
| 税务引擎 | 1–2 人月 | 多税率、价内价外、折算 |
| 审批流引擎 | 1 人月 | 状态机 + 条件 |
| 权限模型 | 2 人月 | 角色/字段/数据范围 |
| 报表引擎 | 2–3 人月 | 聚合、钻取、导出 |
| 文档 + 表单框架 | 4–6 人月 | 动态表单、联动、校验 |
| **合计** | **约 15–20 人月** | 且是"有经验的多人团队"的速度 |

**一个人做，实际是 2–4 年，且质量几乎必然低于 ERPNext**（后者是 10+ 年社区积累 + 上万家公司踩过的坑）。

### 4.4 换底座的真实代价（常被低估的部分）

1. **证据链归零。** C0/M1/A1 三道演练、9 个证据文件、10 类 PDF、九岗位权限矩阵全部要基于新底座重做一遍——而且是在"功能还没完善"的阶段做。
2. **双轨期成本。** 切换期间新底座与 ERPNext 同时存在，同一业务要在两套模型上各实现一遍。
3. **数据迁移。** 已有客户真实数据要从 ERPNext DocType 迁到新模型，且要保证总账逐分相等。
4. **失去上游修复。** ERPNext 的安全补丁、税务法规更新、浏览器兼容都要自己扛。
5. **税务与合规风险。** 记账内核是 ERP 里最不能出错的部分，出错要追溯更正。

### 4.5 关键洞察：换底座和"前端重做"不是一回事

已记录的"底座不行"的表现，绝大多数集中在**表现层与交互层**：

| 表现 | 属于哪一层 |
|---|---|
| 界面偏西方、术语英译中 | 表现层 |
| 单据录入不像传统 ERP、不能表格即表单 | 交互层 |
| 操作步骤多、字段位置不习惯 | 交互层 |
| 不同岗位看到的字段不一样 | 交互层（ERPNext 的 doctype 级权限确实表达不了） |

这些**全都可以在不换底座的前提下解决**，而且 DEC-016 本来就要做。真正属于"底座不行"的只剩两条：**数据模型表达不了某些业务**（目前尚无具体案例）、**长期版本钉死的维护焦虑**。

### 4.6 已定路径：分层抽离

把"换底座"从一个**终局目标**换成一个**接口边界设计问题**：

```
┌─────────────────────────────────────────────┐
│ L1 表现层  自研：工作台、录入表单、报表界面      │  ← 客户直接感知，已在 DEC-016
├─────────────────────────────────────────────┤
│ L2 业务编排层  自研：取价、匹配、导入、视图预设   │  ← N-3/N-4/N-5 都落在这层
├─────────────────────────────────────────────┤
│ L3 领域服务层  自研薄层：只暴露自有契约          │  ← 关键隔离层
│      Business API（自有契约，非 ERPNext 结构）   │
├─────────────────────────────────────────────┤
│ L4 数据与核算内核  暂用 ERPNext                │  ← 唯一可替换的层
└─────────────────────────────────────────────┘
```

**做法**：定义一套自己的 Business API 契约（`docs/DECISIONS.md` 里 "Business API surface and authentication model" 本来就是一条 open decision，现在正好填掉）。L2/L3 只依赖这个契约，**不直接依赖 ERPNext 的 DocType 结构**。

**收益**：
- 现在的开发完全不被拖慢
- 将来若要换 L4，只需实现同一套契约，L1/L2 **零改动**
- 顺带满足 `AGENTS.md` 的"自动化必须走受控的 ERP 服务/API 边界"
- 现在就做，成本只是"多写一层薄适配"；将来不做，成本是"重写整个 L1/L2"

**这也回答了"我已经在改前端"这件事**：前端重做不是浪费，它是抽离的第一步，而且前端做得越独立，将来换底座越省。

### 4.7 终局替换的触发门槛

不以"感觉现在这套不好用"来决定，而是设明确条件：

| # | 触发条件 | 当前是否成立 |
|---|---|---|
| T1 | 真实订单跑完一轮后，仍有核心业务无法用 ERPNext 数据模型表达 | ❌ 真实订单尚未到手 |
| T2 | 上游升级路径断裂，且修复成本 > 自研成本 | ❌ 目前未评估 |
| T3 | 客户明确要求数据完全自主、且愿意承担内核维护责任 | ❌ 未确认 |
| T4 | 有预算与人力完成内核重写 + 全量重新验证 | ❌ 单人项目 |

**当下唯一低成本的动作就是第 4.6 节的契约定义。** 它不产生用户可见功能，但决定了将来换底座是"换适配层"还是"重写系统"。

## 5. D-3 + D-6 前端形态重做（合并项）

### 5.1 合并判断

D-3 说「单据录入和批量录入手感不行，要更贴近传统 ERP」；D-6 说「界面和操作方式偏西方、很多用词是英译中、难以上手」。

这两条指向同一个交付物：**一套符合国内进销存业务习惯的录入与浏览界面**。拆成两个任务做会做两遍，且必然出现「表做成了，但用词和操作仍是英文逻辑」的半成品。

因此合并为一个工作流 **W6 前端形态重做**，内含三个子面：

| 子面 | 内容 | 对应差距分析条目 |
|---|---|---|
| W6-a 录入模型 | 高密度「表格即表单」：一行一商品、扫码、批量导入、字段显隐、录入默认值 | `GUANJIAPO_ERP_GAP_ANALYSIS.md`「商品表格和金额预览」「快速录单和业务默认值」 |
| W6-b 术语与信息架构 | 全部界面词条中文化并对齐管家婆／金蝶用法；左侧分类与右侧内容按国内岗位习惯重组 | `UI_CHINESE_TERMS.md`、`UI_CHINESE_WORKBENCH_PLAN.md` |
| W6-c 操作范式 | 取消西式多步向导与英文式列存交互，改为国内用户熟悉的单屏录入 + 列表即操作 | D-6 原文 |

### 5.2 W6 的现实代价（需要提前认清）

当前工作台是**给原生 Desk 套了层中文导航**（`workbench_catalog.json` 里 8 个分类指向原生表单与报表），并非自定义录入界面。要达到 D-3／D-6 的目标，W6-a 需要为采购／销售／库存核心单据做**自定义高密度录入表单**，这是本项目目前为止**最大的单项工作量**，很可能超过此前所有批次的总和。

所有者确认走丙。试点以采购入库、销售出库为起点，最终以客户实际开单频次和岗位流程确认。内部 Business API 先覆盖两张试点单据所需的操作，试录时同时核对原生库存、审批和权限结果。三条路径如下：

| 路径 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **甲：核心单据定制** | 只对最常用、采购／销售／收付款／出入库四类做自定义高密度表单，其余仍走原生 | 工作量最大，收益最直接 | 自定义表单需自行保证与原生核算链一致，审批、权限、税额计算都要接对 |
| 乙：原生表单增强 | 不做自定义表单，靠字段属性、显示密度、术语、默认值把原生表单调顺手 | 工作量小 | 上限有限，表格即表单这类根本手感改不动 |
| 丙：甲 + 渐进 | 先只做采购入库、销售出库两张最高频单据验证形态，跑通再复制到其余 | 中等 | 需要业务方持续参与形态确认 |

### 5.3 W6 与既有计划的关系

- N-4 的岗位视图预设也并入 W6 同批设计（见第 6 节）。

## 6. N-4 分级权限：岗位视图预设

### 6.1 模式评估

「不同等级的人能看到的内容不一样，前端可以一样，但有的直接锁起来显示没有权限」在产品上完全合理，是"一份前端 + 岗位视图预设"的常见做法。**但有一个铁律**：

> **前端锁住只是体验，后端必须同样拒绝才是安全。**

项目里已有现成范式：`apps/hardware_erp/hardware_erp/approval.py` 的审批守卫——前端呈现与后端校验分离，但后端校验是**决定性的**，前端从不作为唯一防线。岗位权限必须沿用同一原则。

### 6.2 为什么 ERPNext 原生权限不够

ERPNext 权限是 **doctype 级 + 字段 permlevel 级**：

- 能做到"某角色完全看不到某单据类型"
- 做不到"同一个单据，A 看得到成本字段、B 看不到但表单结构一样"
- 做不到"行级过滤"（比如仓管只看自己仓库的单据）

**所以岗位视图预设需要自研**——这是 DEC-016（前端自研）之外的又一个、来自底座限制的明确自研理由，也印证了第 4.6 节的分层判断。

### 6.3 预设抽象

一份配置，按角色 × 单据类型定义：

| 配置项 | 内容 | 前端行为 | 后端行为 |
|---|---|---|---|
| 可见字段集 | 字段名清单 | 不渲染被排除字段 | 提交时剥离/拒绝 |
| 可编辑字段集 | 字段名清单 | 置为只读 | 拒绝修改 |
| 可执行操作 | 提交/审批/作废/退货等 | 隐藏或禁用按钮 | 拒绝越权操作 |
| 必填条件 | 按角色附加 | 动态必填标记 | 强制校验 |
| 可见行过滤 | 条件表达式 | 过滤显示 | 查询时过滤 |

**关键设计原则：一份配置，两处消费。** 前端读它渲染、后端读它校验，用同一份数据源定义，杜绝"前端以为藏了、后端其实能改"的漂移。

### 6.4 三个容易踩的坑

1. **字段隐藏 ≠ 数据隔离。** 隐藏成本字段只是界面行为；采购员若能直接调 API 仍能读到。真正要隔离必须用 ERPNext 的 User Permission / 角色权限在**查询层**生效。这两层要一起做。
2. **锁定后的提示文案要具体。** "没有权限"要说明是"此岗位不可查看成本价"还是"此单据不在你的仓库范围"，否则采购员会反复找管理员。
3. **预设数量会增长。** 9 个岗位 × 单据类型，配置量不小。建议预设可由管理员在界面上组合调整，不要每加一个岗位就找开发改代码。

## 7. N-3 英文原单匹配、中英对照与 ERP 录单

### 7.1 问题陈述

大家英语都不好，每张英文订单都需要一个个去翻译；有时翻译不准确，还要花很多时间找到对应的标准中文五金件名。希望系统能自动模糊匹配并翻译，方便使用。

### 7.2 现有基础比预期好

主数据上**已经有英文名字段**（`apps/hardware_erp/hardware_erp/trade_fields.py`）：

| 字段 | 标签 | 位置 |
|---|---|---|
| `custom_trade_name_en` | 英文商品名称 | Item |
| `custom_trade_requirement_en` | 英文商品要求 | Item |
| `custom_trade_line_requirement_en` | 英文订单要求 | 单据行 |

所以"英文 → 中文标准名"的**一半映射库已经存在**，剩下的是把它从"单个字段"升级成"可检索的别名库"。

### 7.3 真正的问题不是算法，是映射库

采购员要的不是"最像的那个中文"，而是"**这个英文件在我们店里叫什么**"。这要求系统知道：

- 供应商 A 的叫法 ↔ 供应商 B 的叫法 ↔ 客户订单里的叫法 ↔ 我们的标准中文名
- 常见拼写变体（`HEX BOLT` / `HEXBOLT` / `HEX-BOLT`）
- 旧系统里用过但已废弃的名字
- 一个英文描述实际对应多个规格时的歧义

**所以架构是「别名库 + 匹配引擎 + 人工确认回写」的闭环**，而不是"接一个翻译 API"。

### 7.4 已确认的流程

```
英文原单
        ↓  ① 结构化解析（按 N-5 配置加载原单模板）
   原始行：英文描述 / 型号 / 规格 / 数量 / 单位
        ↓  ② 规则层：型号与规格优先（规则匹配，不模糊）
        ↓  ③ 相似度层：n-gram 相似度 + 领域词典分词
   候选 Top-N（中文标准名 + 命中依据 + 置信度）
        ↓  ④ 人工确认（采购员选一个，或新建商品）
   最终匹配
        ↓  ⑤ 回写别名库：英文串 → Item 映射 + 命中依据 + 原单来源
        ↓  ⑥ 生成中英对照新单（保留原文与确认后的标准商品）
        ↓  ⑦ 业务人员依据对照单录入 ERP，形成业务草稿
        ↓  ⑧ 按相应订单的正常审批、提交及履约流程处理
```

**第 ⑤ 步是整个功能的灵魂**：每次人工确认都在扩充别名库，三个月后系统对这家公司的英文单据识别率会非常高。**没有回写，匹配永远停在 50% 准确率。**

### 7.5 算法建议

| 情形 | 方法 | 理由 |
|---|---|---|
| 型号（`M8*30`、`SS304`） | **规则/正则精确匹配** | 模糊匹配反而出错 |
| 规格（`1/2 inch`、`60mm`） | 单位归一化后比较 | `1/2"` 与 `12.7mm` 应等价 |
| 英文描述 | 字符 3-gram Dice 系数 + 领域词典分词 | 短文本上编辑距离误判率高 |
| 完整短语命中别名库 | 字典精确命中，置信度最高 | 复用已积累的别名 |
| 单位（`pcs`/`box`/`ctn`） | 单位词典 + 换算表 | 与 Item 的 UOM 换算复用 |

**必须有的设计约束**：
1. **不自动替换**。高置信度可以预填到待核对行，但必须让人看到并能改。错一个五金件就是错发货，代价远大于多点一次。
2. **每个候选必须给命中依据**（命中了哪个别名/哪个型号），采购员才能秒判。
3. **歧义必须显式呈现**（"3 个候选"），不能静默取第一个。
4. **未匹配的不能丢**，进入待建商品清单——很多英文单据对应的是店里还没建档的新商品。

### 7.6 中英对照单的输出形态

一行一商品，至少包含：

| 列 | 说明 |
|---|---|
| 序号 / 行号 | 对应原单行 |
| 英文原文 | 原样保留，采购员可核对 |
| 中文标准名 | 匹配到的 Item 名称 |
| 规格 / 型号 | 匹配到的标准值 |
| 单位 | 归一化后 + 原单位 |
| 数量 | 换算后 |
| 匹配来源 | 别名库 / 型号规则 / 人工确认 / 未匹配 |
| 置信度 | 百分比或高/中/低 |
| 备注 | 英文订单要求原文 |

中英对照新单首先用于核对和 ERP 录单，支持打印和 Excel，保留英文原文便于追溯。原单上传、匹配和生成对照单属于录单前的准备阶段。仓库后续操作按 ERP 正式业务单据的流程执行。

### 7.7 依赖的真实输入（目前缺）

需要先确认英文原单由客户还是供应商提供，以及录入 ERP 时对应销售订单还是采购订单，再收集 3–5 家相应来源的脱敏样本。需要知道的：

| 需确认 | 为什么 |
|---|---|
| 订单是 Excel 还是 PDF / 图片 | 决定解析方式（PDF/图片需要 OCR，成本差很多） |
| 几家来源方、格式差异有多大 | 决定 profile 数量与维护成本 |
| 英文描述有多长、多自由 | 决定匹配算法选型 |
| 商品编码是否存在 | 有编码就能精确匹配，问题小一半 |
| 数量单位（pcs/box/ctn）出现频率 | 决定换算表工作量 |
| 是否含税、币种 | 决定是否与采购单金额对账 |

**这一项是整个功能的 blocker，优先级应高于编码。**

## 8. N-5 多格式订单导入：配置化，不要写代码分支

### 8.1 两种做法对比

| 做法 | 每来一家新供应商 | 长期运维 | 评价 |
|---|---|---|---|
| **甲：写代码分支**（按 if/供应商判断） | 改代码 → 测试 → 发版 | 发版频率随供应商数线性增长 | ❌ 会压垮单人维护 |
| **乙：配置化 profile** | 填一份 JSON/表单配置 | 现场可自助 | ✅ 推荐 |

**强烈建议乙。** 供应商数量不可控，而项目只有一个人维护。甲方案下第 8 家供应商来的时候，每加一家都要走一次完整发版流程。

### 8.2 按原单来源配置的 Profile

仓库里已有先例可复用：`phase0/migration/mapping-*.json` + `scripts/phase0-preflight-migration.py` 的预检/对账结构。建议 Profile 长这样：

| 配置块 | 内容 | 示例 |
|---|---|---|
| 原单来源 | 按已确认的业务关联 Customer 或 Supplier | `ABC Tools Co.` |
| 文件格式 | Excel / CSV / PDF | `xlsx` |
| 工作表与表头行 | 哪张表、从第几行开始读 | `Sheet1`, `row 3` |
| 字段映射 | 源列 → 目标字段 | `{"Unnamed:2": "item_name"}` |
| 商品标识列 | 用编码 / 用描述 / 用规格 | `描述` |
| 数量与单位 | 单位列 + 换算表 | `{"pc": "件", "box": "盒"}` |
| 日期格式 | 源格式 | `dd/mm/yyyy` |
| 金额口径 | 含税 / 未税 / 不取 | `gross` |
| 匹配策略 | 走 N-3 的别名库匹配 / 编码直连 | `alias_match` |
| 校验规则 | 必填列、数值范围 | `qty > 0` |

### 8.3 导入流程（与现有审批体系衔接）

```
选原单来源 → 加载对应 Profile（可微调）
    → 上传文件 → 解析预览（逐行标红错误，定位到行号列号）
    → 商品匹配（N-3 候选 + 人工确认）
    → 生成中英对照新单
    → 依据对照新单录入 ERP 业务草稿（docstatus=0）
    → 按普通订单的权限、审批和提交规则办理
```

先完成原单处理和对照单生成，再进入 ERP 录单。ERP 录单以草稿起步，由有权限的人员按现有流程提交。模板按客户还是供应商维护，随原单来源确认。

### 8.4 预判的难点

| 难点 | 处理 |
|---|---|
| 单位换算（箱/盒/件） | Profile 声明 + Item 的 UOM 换算表复用 |
| 同一供应商多张表头合并 | Profile 声明多区域映射 |
| 一行多个型号 | 需拆行规则，Profile 声明 |
| 数量为负（退货单） | 识别为退货，方向映射到原单 |
| 金额与订单金额对不上 | 导入时做合计校验，差异列出但不阻断（人工判断） |

## 9. D-4 财务口径延后

所有者决定：成本算法、毛利口径、折算税费率等**放到后续处理，需与财务部协调后确定**。

已记录且不受影响的项：

- `GUANJIAPO_ERP_GAP_ANALYSIS.md` 中已列明的成本算法差异（管家婆全月一次加权平均 vs ERPNext 移动平均）**继续挂起**，迁移前必须对齐，否则毛利对不上——这条不能因延后而消失，只是移到了财务部确认之后。
- 取价优先级（1A）、单据来源关联（2A）不依赖财务口径，可继续推进。

**延后的连带影响（需要留意）**：

1. D-3 的录入体验一旦按真实财务习惯设计（含税录入、整单折扣、优惠分摊、运费入成本），**输入侧就会锁定口径**。若先做完录入界面再和财务部对齐，可能出现界面已定但口径要改的返工。
2. 建议：**接口层先做，口径层后填**。即录入界面的字段位置与交互顺序先按管家婆形态搭好（因为字段集合和操作顺序不依赖具体算法），税率与费用分摊的计算规则留待财务确认后填充，不为合成 5% 税率硬编码。

### 9.1 与财务部的待确认清单（可作为会议材料）

| 项 | 现有合成假设 | 需财务部确认 |
|---|---|---|
| 出库成本算法 | 移动平均（ERPNext 原生） | 全月一次加权平均？是否要切换或分商品配置 |
| 毛利统计口径 | 按出库成本 | 按出库还是按发票确认时点 |
| 折算税费率 | 合成 5% | 法定税率；含税录入与未税录入的换算规则 |
| 整单折扣与优惠分摊 | 合成九折 | 分摊到行还是尾差留在单头 |
| 运费与费用 | 未集成 | 是否入存货成本；是否计入毛利 |
| 应收应付确认时点 | 发票确认 | 预收预付如何核销 |
| 尾差处理 | 原生舍入 | 分币四舍五入规则 |

| 5 | **确认原单来源与目标业务单据，收集 3–5 家对应来源的脱敏样本** | **P0** | 客户侧 | N-3 与 N-5 的共同 blocker；拿不到样本这两项只能停在设计 |
| 6 | W6 前端形态重做：走丙，先试点两张单 | P0 | 第 3 项；正式财务规则依赖第 4 项 | D-3 与 D-6 的落点，工作量最大，需尽早启动 |
| 7 | 岗位视图预设机制（N-4） | P1 | 第 6 项 | 与 W6 同批设计、分开实现 |
| 8 | 英文匹配与别名库（N-3） | P1 | 第 5 项 | 依赖真实样本定算法与别名表结构 |
| 9 | 按原单来源配置导入 Profile（N-5） | P1 | 第 5 项 | 依赖真实样本定 profile 结构 |
| 10 | 取价优先级（1A 剩余）与单据来源关联（2A） | P1 | 无 | 不依赖财务口径，可并行 |
| 11 | 出入库同屏结算（2B） | P1 | 第 4、10 项 | 结算流程是否合并取决于财务确认与业务确认 |
| 12 | 生产服务器选型与域名 | P2 | 无 | Phase 1 前置，不阻塞当前 |
| 13 | 真实数据首轮闭环 | P0（门槛性质） | 第 4、5、10 项 | 用真实商品、客户、价格跑一次，验证取价与单据流程；这是能否上生产的真正判据 |

**两条主线**：
- **第 3 项**决定了将来换底座的代价，必须最早做。
- **第 5 项**是 N-3 与 N-5 的共同前置，且完全依赖客户侧配合，越早发起越好。
